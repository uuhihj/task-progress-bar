# dsh-progress-widget 优化清单（2026-10-24）

## 结论
核心问题不是功能缺失，而是**可配置性为零 + 渲染方式偏粗暴**：所有阈值硬编码、每轮无条件注入协议、前端 1 秒全量重建 DOM。

## A 类 · 值得改（收益明确）

1. **加配置项（最高优先）**
   现状：`cordis.patch.yml` 只有 insert，插件不读任何 config；`POLL_MS=1000`、`DONE_HOLD_MS=30000`、`STALE_RUNNING_MS=30min`、`DONE_KEEP_MS=2min` 全是常量（client.js L9-11、index.js L12）。
   改法：读 patch 的 config，暴露 `pollMs / doneHoldMs / doneKeepMs / protocolHint / maxTasks`。
   影响：用户能自己调频率与行为；成本低（半小时）。风险：需定默认值，别改默认表现。

2. **协议注入加开关**
   现状：`protocolText()` 每轮注入约 150 字（index.js L126-149），无关闭方式。
   影响：长期使用持续吃 token；关掉后失去精确阶段上报。改法：`protocolHint: true/false`，默认 true。

3. **/status 减少同步读盘**
   现状：每次请求都 `readFileSync` 两个文件（index.js L19 READ progress、L28 READ baseline）。
   影响：1 req/s × 每开几个标签页就 ×N；杀毒扫描时会有抖动。改法：缓存 + mtime 校验，或 `fs.watch`。

4. **前端别全量重建 DOM**
   现状：每次轮询 `el.innerHTML = ...` 整体替换（client.js render/renderTask），1 秒一次。
   影响：①每次重建会重置 CSS transition，进度条动画实际被反复打断；②长时间开页面 CPU 偏高；③无法做平滑数字滚动。改法：结构只建一次，之后只改文本/宽度。

5. **主题适配**
   现状：配色写死深色 `rgba(20,22,28,.88)`、`#e8e8e8`（client.js style 块）。用户装了 skin-center（浅色皮肤会被顶）。
   改法：优先读宿主 CSS 变量，取不到再回退深色。

6. **清掉 lib/index.js.bak-20261022**
   现状：15KB 残留备份，未被 git 跟踪、已被 npm files 白名单排除。纯粹是垃圾文件。

## B 类 · 可试（有收益但要设计）

7. **taskMap 淘汰策略**：现在 `size>64` 时删“最早插入”的会话（index.js endTask 分支），多会话长跑时可能误删正在跑的；应按 `lastActivityAt` 淘汰。
8. **损坏进度文件的兜底**：`readTask` 半写入 JSON 会返回 null，任务条直接消失；可保留“最后一次有效值”缓冲 2 秒。
9. **TITLE_MAP 加英文档**：现在全是中文正则（问题修复/功能开发…），英文 prompt 全落空进入截断兜底。
10. **无障碍**：无 `role=status` / `aria-live`，屏幕阅读器读不到进度变化。
11. **彻底隐藏开关**：只能收起成圆点，没有“本会话不显示”。

## C 类 · 不建议做（成本 > 收益）

12. **轮询改 SSE/WebSocket**：数据量极小（几百字节/秒），1s 轮询完全够；换成流式要处理断线重连、连接泄漏、多标签页，收益不抵成本。
13. **加鉴权**：仅监听本地 127.0.0.1，加 token 只会让用户配置更麻烦。

## 外部对照
轮询 vs SSE 的取舍是公开常识：小载荷高频轮询（≤1Hz）成本可忽略，流式的价值在“高频/大载荷”。同类工具（cc-progress 等）也都是轮询。真正该抄别人的地方是**可配置 + 局部更新**，不是换传输层。
